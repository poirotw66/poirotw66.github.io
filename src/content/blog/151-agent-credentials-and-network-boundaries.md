[WIRED 於 2026-10-29 的報導](https://www.wired.com/story/a-defense-contractor-gave-their-personal-ai-agent-access-to-a-secure-pentagon-system)援引匿名消息提出個人 coding agent 存取爭議。Accenture 否認指控有據，DoD 不評論；文中 Anthropic 回應是指向使用政策，並非確認事件。這些說法不足以重建已驗證的資料流或責任。

這類爭議值得提出一個不依賴事件定案的問題：當我們說「讓 Agent 幫忙修程式」，究竟同意了什麼？讀取工作目錄、執行測試、使用既有登入狀態、連接外部服務，乃至部署到正式環境，可能在一次工作流程中接連發生，卻不該被一個模糊的「可以」合併。

本文用公開文件與虛構情境討論這個問題，不還原真實系統，也不判定任何具名公司或個人做錯了什麼。工程上的關鍵是讓每一步需要的權限有明確持有人、執行位置與撤銷方式。

## 先從一個沒有真實憑證的修補情境開始

以下是 Bloss0m 建立的**假想工作流**，不對應報導中的組織、網路或人員，也沒有真實帳號、憑證或實際執行結果。

某團隊希望 Agent 修正報表匯出的小錯誤。它拿到一份已去識別化的程式副本與合成測試資料，可以產生 patch 並在隔離環境測試。測試若缺套件，Agent 可以提出依賴需求；若通過，另一個受控流程檢查 patch，再決定是否進入部署。此時「完成修補」的交付物是可審查的變更與測試證據，不是替人登入所有相關系統。

假設同一台開發機原本還有雲端 CLI 登入狀態、瀏覽器 session、套件 registry token，以及可連線的診斷網站。即使 Agent 沒有被要求讀取這些資料，執行程序可能仍繼承環境或使用可取得的登入資源。設計者因此要問的，不只是「模型會不會主動拿」，還包括「若執行的程式嘗試使用，它在系統層面能不能成功」。

這是控制邊界的假設分析，不是聲稱某個工具必然讀取或外送憑證。把能力與實際行為分開，才能討論可驗證的限制，而不是只推測模型意圖。

## 一句任務指令裡，至少藏著五個不同決定

下面是 Bloss0m 的工程整理，用來檢視上述假想流程；不是任何產品或標準所定義的五層保證。

| 決定 | 假想流程中允許的範圍 | 不能由此推論的權限 |
| --- | --- | --- |
| 任務目標 | 修正指定匯出錯誤並提出 patch | 自行擴大任務或部署到正式環境 |
| 工具與執行程序 | 在限定副本讀檔、改檔及跑指定測試 | 執行任意程式、使用所有本機資源 |
| 身分與憑證 | 測試所需的獨立、有限身分；不需要時不提供 | 繼承人類管理員帳號的完整權限 |
| 網路與資料外送 | 依政策取得核准依賴，傳送必要內容 | 任意上傳日誌、原始碼或診斷封包 |
| 證據與後續動作 | 保存可審查結果並交給下一個流程 | 把工具顯示成功視為已完成安全驗證 |

這張表的用途，是找出權限從哪一欄被偷偷帶到另一欄。允許「讀取錯誤紀錄」不自動允許「把完整紀錄貼到外部診斷服務」。允許「跑測試」不自動允許測試程序使用本機所有雲端身分。允許「產生 patch」也不代表可以自行選擇部署帳號。

NIST 的 [SP 800-207《Zero Trust Architecture》](https://csrc.nist.gov/pubs/sp/800/207/final)於 2020 年發布，將信任重點放在資源與存取判斷，而非只因帳號位於內部網路或資產屬於組織就給予信任。把這個原則用在 Agent 上的工程解讀是：它在受控網路裡執行，仍不足以回答某個身分可對某項資源做什麼；這也不是對前述爭議的鑑識結論。

## 確認視窗和 sandbox 各自回答不同問題

截至 2026-11-02 的 Claude Code 官方 [permissions 文件](https://code.claude.com/docs/en/permissions#how-permissions-interact-with-sandboxing)將工具權限與 sandbox 視為互補層。前者處理工具與動作能否被允許，後者限制執行程序可觸及的檔案及網路。是否提示還與模式及規則有關，不能把某個畫面的確認提示當成跨版本、跨工具的統一行為。

對假想團隊而言，確認視窗適合讓人判斷具體變更，例如「是否接受這份 patch」；它卻不是要求審查者在看一行測試命令時，同時推演每個相依套件、子程序、既有登入狀態與遠端 API 的全部效果。反覆詢問也不能替代明確限定執行環境。

官方 [sandbox 文件](https://code.claude.com/docs/en/sandboxing)特別說明，shell sandbox 的涵蓋範圍是 shell 命令與其子程序，其他檔案工具、MCP servers 與 hooks 不在同一個邊界內。它也有獨立的憑證、檔案與網路設定。因此「開啟 sandbox」仍需追問：是哪個程序、哪種資源、哪些例外？不能由此宣稱整個 Agent 的所有管道都已隔離。

Bloss0m 的設計建議是，把低風險且範圍固定的動作交給可重複執行的限制，把人的判斷保留給有意義的交付與權限轉換。若缺套件，應提出明確的依賴需求；不能因為測試沒有通過，就順手擴大執行權限、讀取更多憑證或開放整個網路。這是流程建議，並非本文測得某種設定可防止所有攻擊。

## 允許連到一個網站，也沒有回答准許送什麼

在假想流程中，套件鏡像、程式碼託管平台與診斷服務都有看似合理的用途。但是，目的地屬於允許名單，只回答一部分連線問題。上傳內容、遠端帳號的權限、服務保存方式，以及回應內容能否影響後續操作，仍要分別判斷。

例如，下載核准套件和上傳完整測試日誌，可以連向同一個服務體系，卻有不同的資料風險。日誌即使沒有密碼，也可能含內部路徑、客戶識別資訊、環境變數或系統結構；在這個假想情境裡，安全的下一步是先產生可審查、縮減過的診斷內容，必要時由獨立流程外送，而不是假定「能連線」等於「可以傳全部」。

外部文件、套件說明或服務回應也可能包含指令式文字。Claude Code 的官方 [security 文件](https://code.claude.com/docs/en/security#protect-against-prompt-injection)將 prompt injection 列為需防護的風險，並說明權限與隔離措施。這支持把外部內容視為資料來處理，而不是自動授予它修改工作目標或索取憑證的權力；它不證明報導中的事件由 prompt injection 引起，也不保證特定產品已消除該風險。

另一個容易混淆的地方是身分：Agent 服務帳號、開發者本人的帳號、模型服務訂閱，並不是同一份授權。就算使用者合法登入某個模型服務，也沒有因此取得把另一個組織資料傳給該服務的權利。反過來說，組織核准某種模型服務，也不代表任何工作負載都可以使用管理員憑證。

## 稽核要追得回權限轉換，不只留下一段聊天

回到假想團隊，最有用的證據應該能回答：這份 patch 由哪個任務產生？測試在哪個受限環境跑？用了哪個身分？曾向哪些目的地發出請求？哪些動作被拒絕或升級給人？誰接受了變更，又是誰授權部署？

這是 Bloss0m 的稽核設計建議，不是說任何一套工具目前都會完整記錄上述資訊。只存對話容易漏掉子程序和服務端動作；只存網路紀錄則未必知道那次連線對應哪個任務。兩者需要可關聯的工作與操作識別，才有機會把來源、執行及接受決策串起來。紀錄本身也應遮蔽秘密，不能為了可追查而再複製一份完整憑證。

若測試結果顯示曾嘗試未核准的連線，第一個問題應是該次嘗試被哪一層阻擋、身分是否仍有效，以及同一環境還有沒有其他可用管道；不是只問 Agent 是否口頭承認。必要的停止、撤銷身分與保留證據，也應由可操作的控制程序處理。這仍是概念情境，不表示任何具名事件發生了這些步驟。

> **花花的工程提醒**
>
> 「我同意你完成這個任務」需要被轉成幾個可驗證的授權：在哪裡執行、用誰的身分、接觸哪些資料，以及結果能往哪裡送。聊天裡的一個「可以」不能代替這些邊界。

對要導入 coding agent 的團隊，現在就能做的一個有界檢查，是拿一個沒有真實秘密的合成任務，逐步標出「讀取副本、執行測試、取得依賴、提交 patch、授權部署」之間每次權限轉換，並確認拒絕時誰能實際阻止下一步。是否採用某個產品，應建立在這些可檢查條件與自己的資料政策上，而不是建立在對爭議報導的推測，或只因 Agent 看起來能順利完成工作。
