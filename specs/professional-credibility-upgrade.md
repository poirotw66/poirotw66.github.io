## 1. 目標與核心決策

讓訪客從「網站好看、內容很多」進一步理解「Justin 解決過哪些問題、如何做決策、有哪些成果可以查驗，以及適合邀請他做什麼」。

本次採用有溫度的工程出版與作品展示方向，沿用 Astro、現有語意 token、暖色／深色與既有品牌。視覺差異度中等、動態低、資訊密度依摘要與深讀分層；不以增加動畫作為升級主軸。

### 1.1 可驗收目標

1. 首次訪客在 30 秒內能說出作者的專業領域、至少一個代表專案，以及主要貢獻。
2. 每個首頁成果訊號，都能在一次點擊後找到對應的版本、範圍與證據說明。
3. 三個代表案例各自呈現具體責任、技術取捨、真實產出與限制。
4. 技術主辦方在聯絡頁可直接取得簡介、主題與聯絡方式；有可公開素材時可下載講者資料。
5. 桌面與手機的關鍵圖像可理解、圖說完整，雙語內容與成果口徑一致。

以上是產品與驗收目標，不宣稱已由使用者研究或正式站數據證明。

### 1.2 範圍與非目標

本次先處理首頁、三個旗艦案例、專案列表、關於與聯絡頁，以及首頁精選的三篇工程文章。論文頁僅做共用樣式回歸，不展開全站內容重寫。

- 不重做品牌、導覽、路由、Astro 技術棧與主題系統。
- 不新增 CMS、會員、訂閱後端、即時 AI Demo 或付費服務流程。
- 不為了專業形象補造客戶、職稱、使用量、效益、推薦語或正式環境經驗。
- 不把發布規格視為 commit、push 或部署指令；本文件本身只交付規劃。
- 不批次重製所有封面，不要求公開私人程式庫或原始企業資料。

| 訪客 | 第一個問題 | 主要路徑 | 完成訊號 |

## 4. 成果與證據資料契約

### 4.1 成果分類

| 類型 | 例子 | 展示限制 |
| --- | --- | --- |
| 評測結果 | RAG 加權準確率、平均延遲 | 必須有版本、方法、樣本與限制；不同測試不得暗示同一實驗 |
| 實作範圍 | 19 個子流程、5+ 醫院格式 | 明確標為功能／格式覆蓋，不等同使用量、品質或可靠度 |
| 營運結果 | 正式流量、SLA、人工工時改善 | 只有取得可公開依據才展示；本次不預設存在 |

「沒有錯誤答案」「沒有例外／逾時」「沒有不安全回答」是不同量測項，不得相互替代。固定題庫反覆調整的分數不能推論未知題目的泛化表現。

### 4.2 擬新增共用資料

擬新增 `src/data/projectEvidence.ts` 作為網站展示成果的唯一結構化來源。此檔是本次建議新增，尚不存在；不得放入私人報告全文、內網網址或機密資料。

每筆成果至少包含：

| 欄位 | 要求 |
| --- | --- |
| `id`／`projectSlug` | 穩定識別，例如 `rag-v22-weighted-accuracy` |
| `kind` | `evaluation`、`capability` 或 `operational` |
| `value`／`unit` | 實際數值與單位；未取得數字不填 0 |
| `label` | zh／en 名稱 |
| `version`／`measuredAt` | 已知版本與實測日期；未知值為 null，不使用文章更新日替代 |
| `scope`／`method`／`limitations` | zh／en 的樣本、計算方法與適用邊界 |
| `sourceStatus` | `public-artifact`、`author-reported`、`pending-verification` |
| `publicSourceHref` | 可公開的原始成果／附件連結；沒有則為 null |
| `detailAnchor` | 指向案例內對應證據段落 |

規則：

1. `pending-verification` 不渲染為首頁成果數字；改用已確認的實作描述，或移除該成果項。
2. `author-reported` 可保留有依據的作者報告，但顯示「作者評測摘要；原始報告未公開」等準確說明。
3. 連到自己另一篇文章只是延伸閱讀，不能當作獨立驗證或公開原始評測。
4. 中文與英文共用數值、版本、日期與狀態，只有敘述本地化。
5. 首頁 trust、案例 metric 由 ID 引用同一資料；`homeBrand.ts` 保留問題、方法與簡介文案。
6. Markdown 詳細敘事可保留數字，但需在遷移清單列出位置，驗收比對同一成果 ID 的版本與口徑。不要為抽取數字而將全站改成 MDX。
7. 現有 frontmatter `impact`／`tldr` 若保留成果數字，需同步校正；三個案例的列表預覽優先透過共用資料 formatter 產生，其他專案維持既有 fallback。

## 6. 案例頁：快速理解與深入查驗

### 6.1 共用版面

沿用 `ProjectPostContent.astro` 與 `EngineeringCaseStudy.astro`，合併 ArticleBrief、案例 summary 與正文摘要中的重複句子。

```text
名稱、日期／更新資訊
一句問題 + 我的責任 + 已核實成果與限定說明
代表圖版（含圖說）
頁內入口：架構決策 / 評測與限制 / 技術細節
問題與限制
架構與技術決策
我的具體責任
評測方式與成果
失敗、修正與驗證
證據與延伸資料
技術實作細節
相關閱讀／既有聯絡入口
```

- 快速摘要目標繁中 120–180 字、英文 80–120 words；必要口徑不為字數犧牲。
- 不重複堆出完整 TL;DR、完整工程摘要、完整正文摘要三套相同內容。
- 保留 `case-context`、`case-design`、`case-role`、`case-evaluation`、`case-failures`、`case-evidence`、`technical-implementation-notes`。
- 原正文標題錨點若移動或刪除，保留相容 anchor；移動不改變引用的意思。
- 摘要與深讀目錄分組；手機可展開，但正文與成果預設可見。
- 桌面閱讀欄與寬圖分開，手機 DOM 順序即視覺順序。

### 6.2 Agentic RAG：第一優先

交付四項核心材料：

1. **摘要**：問題、本人責任、一個主要決策、版本化成果、主要限制。
2. **代表架構圖**：沿用可查驗系統架構，首頁簡化圖與深入架構圖各有用途，不重複展示同一張密圖。
3. **評測說明**：品質與延遲分組，交代版本、樣本、評分、環境與未知條件。
4. **失敗分析**：從既有真實教訓挑 1–2 個深化，不另造故事。

決策敘述須呈現「限制 → 比較過的方案 → 選擇理由 → 代價 → 何時改選」。若無證據顯示曾測試替代方案，標為設計考量，不寫成已做實驗。

優先失敗案例候選：Swagger filter placeholder 導致 BM25 過濾異常；每題先呼叫 LLM 造成延遲。每則說明症狀、定位依據、修正與驗證方式。缺少 log 或前後數字時明示只有實作紀錄，不能生成假的量測圖。

評測表至少分成「v22 品質」與「後續 rule-first 延遲」。不將加權正確率稱為全面安全保證，不把固定 100 題宣稱為獨立測試集，除非來源證實。

### 6.3 OCR：第二優先

- 將代表圖整理為「可公開輸入 → 區域偵測 → JSON 輸出」。已有去識別真實素材優先。
- JSON 示範使用合法 JSON；說明哪些欄位對照來源，避免示例與實際截圖不一致。
- 補清楚欄位驗收範圍、低解析度與特殊版型的人工覆核條件。
- 若沒有字元／欄位準確率或工時統計，成果聚焦格式覆蓋與結構化輸出。
- 無法公開原始收據時使用另行建立的合成測試資料並明示，不能將其寫成真實驗收樣本。
- 病患資訊、帳號等不應出現在新增公開素材；去識別後重新檢查圖片、檔名與 metadata。

### 6.4 LINE／n8n：第三優先

- 用一張概覽顯示主路由與模組群組，完整 19 子流程另附清單或可公開匯出。
- 選一條已有證據的路徑展示輸入、意圖判斷、子流程、回應。
- 交代 timeout、失敗回應、重試與人工接手哪些已實作、哪些尚未實作。
- 展示本人負責的串接、路由與維護邊界，不把所用第三方模型能力當作本人研發成果。
- 沒有成功率、流量或維運紀錄時，不寫「穩定路由」「正式環境可靠度」等量測暗示。

### 7.2 視覺規則

- 延續暖色奶油／銅色與深色海軍藍／藍色，不建立另一套 palette。
- 同組工程圖統一字體、箭頭、線寬、圖例與語意。節點標題採 HTML 或可維護 SVG 文字；不以生成式圖片承載精確流程與數字。
- 可用 AI 協助概念插畫，但必須與實際架構／截圖區分，不生成假的產品畫面或評測圖。
- 專案封面沿用 16:10，含字與完整流程採 contain。作者照片可用 4:5；社群分享圖使用獨立 1200×630 版本或傳入實際尺寸。
- 圖說包含「看什麼、來源／版本、實測或示意」；圖說是理解內容，不是裝飾標籤。
- 手機簡化圖的主要文字目標至少 14px；無法達成時拆圖、提供文字等價說明與原圖入口。
- 寬表格可在局部橫向捲動，頁面本體不得溢位；圖表不用顏色作唯一辨識。
- 新增正文／展示 raster 目標手機 ≤100KB、桌面 ≤180KB；社群圖獨立記錄大小。這些是素材目標，不取代現有 build budget。
- 圖片設定寬高／比例與響應式來源，僅必要 LCP 圖 eager；影片採預覽與點擊播放，不自動播放。

擬新增 `docs/reviews/professional-credibility-assets.md`：記錄用途、來源、公開權限、版本、尺寸、bytes、alt、裁切與雙主題檢查結果。採用新專案封面時遵循既有 `bloss0m-project-cover` 技能；此 SPEC 不要求全面換封面。

## 8. 作者與講者頁

沿用 `/contact/` 及英文對應路由，保留主要導覽名稱。

### 8.1 頁面順序

1. 作者名稱、專業定位、自然照片（有素材時）與現有邀請 CTA。
2. 工程經驗：3 項具體責任，每項連回代表案例或已存在的工程文章。
3. 代表演講：日期、活動、題目、聽眾收穫、官方活動連結；錄影／投影片有資料才顯示。
4. 可以分享的主題：沿用三個主題，各補適合對象與可帶走的內容。
5. 講者資料：短簡介、較長簡介、可下載照片與投影片連結。
6. 編輯與研究方法：保留既有一手證據、AI 協作、作者責任與更正原則。
7. 邀請資訊：對象、主題、形式、日期與聯絡方式，沿用 Email／LinkedIn。

### 8.2 講者資料規格

- 短簡介：繁中約 80–120 字、英文約 60–90 words。
- 長簡介：繁中約 200–300 字、英文約 150–220 words。
- 以頁面可選取文字為第一版，下載 `.txt` 作漸進增強；無需新增 PDF 產生依賴。
- 照片下載只提供確定可供活動使用的版本，註明署名需求。
- 不自動補公司、客戶、服務年資或職涯日期；未提供的資料不留可見 placeholder。
- 未確認已舉辦的活動不得放進「已完成演講」；若確定是未來活動，清楚標示預告。
- 此次不新增收費、顧問服務承諾或聯絡表單後端。

## 10. 閱讀、分享與無障礙收尾

- 中文與英文分別校對標題斷行、行寬、標點、日期與圖說，不以縮小字體塞滿畫面。
- 沿用手機長文 17px／1.8、既有 900px／640px 主要斷點及字體系統。
- 確認 Windows 與可取得的其他平台中文 fallback；未測平台記錄限制，不假設字型已載入。
- 不增加連續進場動畫或依賴 JS 才可見的關鍵內容；新增圖像揭露使用者可控制。
- 對比、可見焦點、鍵盤導覽、44×44px 觸控範圍維持既有規格。
- 首頁、三案例、聯絡頁與三精選文章檢查 title、description、canonical、hreflang、OG／Twitter 與 JSON-LD 的一致性。
- 社群圖的 metadata 尺寸必須符合實際圖片；16:10 封面不得假標 1200×630。
- 社群平台實際預覽可受快取影響；分開記錄 HTML 正確性與平台實際抓取結果。
- 不新增無依據的 rating、review 或成果結構化資料；只保留對應真實頁面的 Person／ProfilePage／CreativeWork 等既有語意。

## 12. 分階段工作包與交付順序

以下工時是規劃估計，以素材可用、無大規模重畫為前提，不含等待作者資料與部署時間。

| 階段 | 工作 | 交付與退出條件 | 估計 |
| --- | --- | --- | --- |
| P0 現況與證據盤點 | 核對本地／正式版本、現有驗收、成果來源與素材 | 證據清單、素材清單、待確認項與基準截圖 | 0.5–1 日 |
| P1 RAG 與共用成果 | 成果來源整合、RAG 摘要／評測／失敗、首頁口徑同步 | 中英 RAG 與首頁可 review；數值與版本一致 | 1.5–3 日 |
| P2 其他案例與圖像 | OCR、LINE 材料精修、列表文案一致 | 兩案例中英、真實圖版、限制與本人責任 | 1–2 日 |
| P3 作者與講者 | 聯絡頁、照片、演講與簡介 | 作者頁中英、講者文字資料、素材來源紀錄 | 0.5–1.5 日 |
| P4 精選與品質收尾 | 三篇精修、內鏈、分享預覽、回歸 | 中英精選、完整驗收紀錄與剩餘限制 | 1.5–3 日 |

建議第一個獨立交付範圍為 P0＋P1。後續每階段保持可單獨檢視與回復；已核對的材料可先完成，不等待所有照片或私有報告。

### 12.1 資料缺口處理

| 缺口 | 誰提供／核對 | 可先完成的工作 | 最終處理 |
| --- | --- | --- | --- |
| RAG 原始評測與計算規則 | 作者確認可引用內容，實作者核對呈現 | 摘要分層、版本拆分、資料模型 | 無原始公開附件則標作者報告；無法確認數值則撤下突出展示 |
| 實際責任／協作範圍 | 作者確認 | 整理現有描述與待確認清單 | 不加未知履歷；保留已確認責任 |
| 正式環境證據 | 作者確認可公開範圍 | 使用中性工程案例名稱 | 無依據維持中性用語 |

| 原始 workflow／trace | 作者提供可公開輸出 | 概覽圖與已有實作描述 | 無證據不補造執行結果 |

## 13. 測試與驗收矩陣

### 13.1 內容與資料

- [ ] 三案例每個突出成果都有 ID、類型、版本／未知註記、範圍、來源狀態與案例定位。
- [ ] zh／en 共用數值與狀態；首頁、列表、案例摘要與正文口徑相同。
- [ ] RAG 品質與延遲分組，沒有把錯誤答案與程式例外視為同一指標。
- [ ] 19 子流程與 5+ 格式明確屬實作範圍，沒有轉成品質／營運保證。
- [ ] 正式環境、穩定性與個人主導等用語都有相應依據，否則已收斂。
- [ ] 私有原始報告與公開證據摘要有清楚區分，延伸文章不冒充獨立驗證。
- [ ] 三案例都有本人責任、取捨、真實材料與限制；未知資料沒有被補造。
- [ ] 作者與演講素材可公開，三篇精選保留來源、適用邊界與中英一致性。

### 13.2 視覺與互動

主要矩陣：首頁、專案列表、三案例、聯絡頁，各測 390×844 與 1280×800，zh／en × warm／dark，共 48 組頁面狀態。

三篇精選文章各測手機／桌面與雙語，兩主題皆抽查；若共用長文樣式有變，擴充為三篇完整雙主題矩陣。

另外：RAG 與聯絡頁檢查 768px、320px、200% 縮放；共用殼層若修改，補測部落格列表、論文長文、搜尋與 404。

- [ ] 30 秒摘要與主要入口可掃讀，沒有三套重複摘要。
- [ ] 圖像主要內容不裁切，密圖有文字等價說明／原圖入口。
- [ ] 手機沒有整頁橫向溢位；鍵盤、目錄、舊錨點正常。
- [ ] JS 不可用及 reduced motion 下，成果、來源與聯絡方式可取得。
- [ ] 對比與字級符合 UI guideline；圖片不造成可見版面跳動。
- [ ] 分享圖、alt、尺寸與本地化 metadata 正確。

### 13.3 自動檢查

實作階段按實際修改範圍執行：

| 變更 | 檢查 |
| --- | --- |
| 共用成果資料與首頁 | `npm run test:home-brand`；必要時新增成果資料行為測試 |
| 內容／雙語 | `npm run check:content`、`npm run check:i18n`、`npm run test:i18n`；文章再跑相關閱讀品質與格式檢查 |
| 圖像衍生流程 | `npm run test:covers`、`npm run check:image-budgets` |
| 目錄／錨點 | `npm run test:toc` 及實際 DOM 連結檢查 |
| 首頁閱讀路徑有改動 | `npm run test:home-roadmap`、`npm run test:home-roadmap:render` |
| 最終實作 gate | `npm run build`，成功後執行 `npm run test:performance` |

新增測試應驗證：未知來源不顯示突出數字、不同版本不被合併、中英共用成果，以及證據入口存在。不要為純間距／色彩建立鏡像測試。

效能預算以 `scripts/check-performance-assets.mjs` 與現有 Lighthouse 設定為準，不放寬門檻。LCP≤2.5s、CLS≤0.10 為體驗目標；本地測試不宣稱證明正式站 INP。此文件新增本身只需文件與路徑檢查，不必為純 SPEC 跑全站 build。

### 13.4 小型任務驗證

有條件時找 3 位未參與改版的人，至少涵蓋工程師與非工程主辦／招募視角：

1. 看首頁 30 秒，說出作者專業與一個具體成果。
2. 找到該成果的版本與限制。
3. 說出一項作者負責的工作與一項技術取捨。
4. 找到邀請演講所需的資訊。

記錄是否完成、卡住位置與誤解，不以主觀「好看」作唯一結論。每項至少 2／3 人完成是初步迭代門檻，樣本太小不作統計推論。未做真人測試時標為待驗證，不以實作者自評代替。

## 14. 上線後觀察與完成定義

若現有分析工具已有相關事件，觀察首頁到案例、案例到證據、聯絡入口的使用；不新增追蹤服務、不更名既有事件。缺少事件時先記人工任務結果，不為本次增加分析後端。

上線後可比較相近流量來源的 2–4 週資料，記錄內容與流量變動；不承諾轉換率提升比例，也不把同時發生的成長全部歸因改版。

實作驗收擬記錄在 `docs/reviews/professional-credibility-acceptance.md`，包含日期、commit／工作樹版本、頁面、viewport、語言、主題、截圖位置、測試結果與未完成項。

本規格完成實作必須同時具備：

1. P1–P4 交付及必要雙語內容完成，或個別可選素材採本規格的明確 fallback。
2. 突出成果都能追溯到準確的來源狀態與限制。
3. 案例、作者與精選內容形成連貫閱讀路徑。
4. 視覺與必要功能矩陣、build、效能 gate 通過並有紀錄。
5. 尚未取得的照片、私有附件、跨平台與真人測試明列限制，不標成已完成。

第一個可交付里程碑是「RAG 代表案例與首頁成果同步完成」，整體完成狀態需等剩餘階段驗收後更新。本文件目前仍為 Proposed。
