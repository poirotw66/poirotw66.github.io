When engineering shifts from "humans writing code" to "agents generating code," the most expensive resource is no longer API usage, but human time and attention. In this engineering post, OpenAI uses an internal product experiment with almost no manual coding to explain that for agents to deliver consistently, the "engineering environment" must be built as a readable, verifiable, and enforceable harness.

The value of this article lies in its attribution of success not to a stronger model, but to actionable engineering infrastructure—from knowledge maps (`docs/` and `AGENTS.md` personas), to end-to-end reproducibility (UI, logs, metrics), to layered architectural boundaries (cross-cutting concerns entering through a single interface).

> When code is generated by agents, the core job of the Harness is to engineer "feedback loops, architectural boundaries, and observability" so that errors can be detected and fixes can be carried forward, rather than relying on prompts and hoping the model figures it out.

---
### Background: The Engineer's Role Rewritten as "Building Environments and Feedback Loops"

OpenAI describes how their team delivered an internal Beta product in five months, where "humans never directly wrote any code." All application logic, tests, CI configurations, documentation, observability, and internal tools were written by Codex. They estimated the overall workload took only about **1/10** of the time compared to coding manually.

In terms of manpower scale, the small team driving Codex consisted of only **three engineers**, and the codebase eventually accumulated about **one million lines of code**, opening and merging approximately **1,500** pull requests during that period; when the team grew to seven engineers, throughput actually continued to increase.

OpenAI also noted that the reason progress slows down is often not because Codex isn't capable enough, but because the environment specifications are not clear enough: the agent lacks the tools, abstractions, and internal structures required to complete the task. Therefore, the main task of engineers becomes making sure the agent "can understand, can execute, and can continue working after finishing."

---
### Core Concept 1: Using Knowledge Maps Instead of "Thousand-Page Manuals"

Long context is certainly important, but OpenAI's early lesson was: giving an agent a massive `AGENTS.md` (or similar single monolithic file) often fails on several levels:

- Background information becomes a scarce resource: Huge instruction files crowd out tasks, code, and relevant documentation, causing agents to miss key constraints or optimize in the wrong direction.
- Too much guidance becomes non-instruction: When everything is "important," the agent instead resorts to local pattern matching rather than conscious navigation.
- Documentation rots in real-time: A large manual is hard to verify for coverage and freshness, eventually becoming a graveyard of stale rules.
- Hard to verify: A single hodgepodge is detrimental to mechanical checks like coverage, freshness, ownership, and cross-links.

Therefore, they transformed `AGENTS.md` from an encyclopedia into a "table of contents": the codebase knowledge base resides in a structured `docs/` directory, while `AGENTS.md` serves only as a map of about **100 lines**, injecting context while pointing to other truer sources.

Taking it a step further, the updating of the knowledge base is not monitored by humans: dedicated linters and CI verify whether the structure and cross-links are correct, and a periodically running "doc-gardening" agent scans for outdated or unused documentation, directly opening pull requests for fixes when necessary.

---
### Core Concept 2: Enabling Agents to "Verify End-to-End" Instead of Just Reading Code

As code throughput increases, human QA becomes a bottleneck; OpenAI's approach is to make information like UI, logs, and application metrics directly understandable by Codex, and reproducible and reason-able by the agent.

For example, they allow the application to be launched via `git worktree`, enabling Codex to spin up isolated instances for each change; meanwhile, they connected the Chrome DevTools protocol to the agent's runtime, and built skills to handle DOM snapshots, screenshots, and navigation, allowing Codex to reproduce bugs, verify fixes, and reason about UI behavior.

In terms of observability, they adopted the same principle: logs, metrics, and trace data are exposed to Codex as a local observability stack, and the agent tears down the corresponding isolated version after the task is completed. This makes prompts like "ensure the service starts within 800 milliseconds" or "no span in the four key user journeys exceeds two seconds" feasible because the agent has querying tools (like LogQL and PromQL).

To the outside world, this capability means Codex can run continuously and complete a single task (often taking more than six hours) while humans are sleeping.

### Core Concept 3: Enforcing Layered Architecture and Boundaries to Mechanize "Structural Consistency"

Documentation alone is not enough to maintain the consistency of a codebase entirely generated by agents. OpenAI chose to replace exhaustive implementation management with "boundary invariants": parsing data shapes at the boundaries without restricting which library the model uses; restricting dependency directions and allowed sets of boundaries within each business domain; and mechanically enforcing these through custom code format checkers and structural tests.

The example mentioned in the article is the use of a layered domain architecture, where cross-cutting concerns (such as validation, connectors, telemetry, feature flags) enter through a single explicit `Provider` interface; apart from this, everything else is strictly disallowed. The layering sequence is roughly `Types → Config → Repo → Service → Runtime → UI`, and this rule is made adherable through automatic checkers and structural tests.

![Rule schematic of layered architecture and cross-domain interface boundaries](/blog/11-harness-engineering/OAI_Harness_engineering_Layered_domain_architecture_with_explicit_cross-cutting_boundries_desktop-light.webp)

Such constraints are usually engineering efforts undertaken by large teams scaling to hundreds of engineers; but for coding agents, it is instead an early prerequisite: constraints allow speed to be sustained without degradation or architectural drift.

---
### Core Concept 4: Accepting the Limits of Agent "Accessible Knowledge" and Internalizing Key Context into the Repo

OpenAI emphasizes: to an agent, anything it cannot access in context at runtime effectively does not exist. Thus, "knowledge availability" is not an abstract problem, but a requirement to turn context into repo artifacts that the agent can see, reason about, verify, and directly modify.

They point out that over time, more and more context needs to be pushed back into the repository: for instance, if the agent cannot find the team's discussions aligning on architectural patterns on Slack, it will be as blind as a new hire three months later.

Therefore, they prefer to internalize dependencies and abstractions within the repo, and through versioned artifacts (code, Markdown, schemas, executable plans), enable the agent to continuously make consistent inferences based on "everything it can see."

### Data / Observation: Throughput Changes Merge Philosophy and the Need for "Garbage Collection"

In a system where agent throughput far exceeds human attention, OpenAI believes many traditional engineering norms lose their effectiveness. They adopted less blocking merge gates: pull request lifecycles are shorter, and test flakiness is usually handled through subsequent re-runs rather than indefinitely blocking progress.

At the same time, full agent autonomy also brings the problem of "AI sludge replication": Codex will duplicate existing patterns in the codebase, even if they are inconsistent or sub-optimal patterns, which over time leads to drift. In the past, teams originally spent time on Fridays cleaning up AI sludge, but this didn't scale well.

So they institutionalized "golden rules" into the codebase, and established a fixed-cycle cleanup mechanism, proactively scanning for deviations, updating quality ratings, and opening targeted refactoring pull requests; most changes can be reviewed and auto-merged within a minute. This is architecturally akin to garbage collection: technical debt accumulates at high interest, and paying it off consistently in small installments is usually better than letting compound interest run wild.

---
### Takeaways and Recommendations: Building "Long-Term Maintainable" Harness Engineering

To condense this article into actionable practices, I would give four engineering-oriented recommendations:

1. Shift specifications from "prompts" to "mechanically checkable": Use linters, CI, and structural tests to encode invariants into the system, not in a corner of a document.
2. Make knowledge into maps, not encyclopedias: Use short tables of contents + structured docs, and let doc-gardening continuously maintain freshness and cross-links.
3. Turn feedback into end-to-end verification: Hook UI, logs, and metrics into toolchains the agent can query and drive, so bugs can be reproduced and fixes operationally verified.
4. Internalize the "agent-accessible world": The context you want the agent to understand must exist as repo artifacts; otherwise, even if humans think "it should know," the agent won't.

---
### Conclusion

OpenAI's core message is: As agents take on more of the code lifecycle work, engineering discipline still exists, but it looks more like a set of frameworks and feedback loops, rather than humans manually patching code line by line. Good harness engineering makes errors observable, allows fixes to be continued, maintains architectural consistency under high throughput, and ultimately saves human attention for truly scarce decisions and trade-offs.
